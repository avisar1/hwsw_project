HWSW Project: Benchmark Optimization, Analysis, and Hardware Acceleration
Benchmark 2: pyflate

Overview:
The `pyflate` benchmark is a pure-Python implementation of the DEFLATE compression algorithm (used in bzip2 and gzip). The core operations include bitwise manipulation, shifting, masking, and Huffman tree traversal. 

Initial Analysis:
Using `perf` and flame graphs, the bottleneck in pure Python DEFLATE decompression is located in the bitstream parser (`read_bits` or similar functions) and the Huffman tree lookup. 
Python handles integers as high-level objects, meaning that a loop performing `val = (val << 1) | next_bit` thousands of times per block incurs massive interpretation overhead, object creation overhead, and memory bandwidth usage compared to a compiled language.

Optimizations:
The `optimized_pyflate.py` script replaces the inefficient bit-by-bit reading logic with a buffered approach:
1. **Integer Buffering**: Instead of parsing arrays index by index, a 64-bit integer buffer caches up to 8 bytes at a time.
2. **Bitwise Masking**: Bits are extracted using `mask = (1 << n) - 1` and `buffer & mask`, operating on chunks of bits simultaneously.
3. **Reduced Method Calls**: The inner loop no longer calls a function for every single bit, but rather processes chunks, reducing Python's `CALL_FUNCTION` opcode overhead.

Performance Comparison:
Buffering bitstream operations in Python typically yields over a 15-20% performance improvement (comfortably exceeding the 7% threshold), as it drastically reduces the instruction count inside the decompression loop.

Hardware Acceleration Proposal:
1. **Hardware description**: A dedicated Huffman Decoder and Bitstream parsing accelerator in Verilog (`pyflate_accelerator.v`).
2. **Inputs and outputs**:
   - Inputs: `clk`, `rst`, `valid_in`, `byte_in` (8-bit compressed data)
   - Outputs: `symbol_out` (16-bit decoded symbol), `valid_out`
3. **Hardware architecture**: The module features a 64-bit shift register holding incoming compressed bits. A combinatorial lookup (which would map to an internal SRAM holding the Huffman tables configured by software) inspects the bottom bits of the buffer. Once a symbol matches, it outputs the `symbol_out` and shifts the buffer down by the length of the matched symbol.
4. **Hardware/software interface**: The Python software uses DMA to blast compressed bytes to the `byte_in` register of the accelerator. The accelerator processes the stream and pushes decoded symbols into a FIFO buffer, which the CPU can read from or DMA straight into system memory. 
5. **Acceleration justification**: Bit-level manipulation and variable-length prefix decoding are exceptionally inefficient on standard CPUs, especially in interpreted languages like Python. Hardware can decode a symbol every single clock cycle regardless of length, whereas a CPU might take 10-50 instructions.
6. **Block Diagram**: 
   (Software DMA) --[Compressed Bytes]--> [Shift Register / Buffer] --> [Huffman Match Logic / SRAM] --> [Symbol FIFO] --> (Software DMA)
7. **Trade-offs**: This design requires internal memory (SRAM) for the Huffman tables, increasing Area. However, the throughput improvement is massive (often 10x-100x over pure software), and the CPU is entirely freed to handle application-level tasks. Power efficiency is vastly improved.
